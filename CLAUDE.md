# EOS Tracker

A single-page tool for tracking EOS (Entrepreneurial Operating System) goals and quarterly Rocks.
Originally built as a Claude.ai artifact; the original conversation is not available, so this file is the source of context.

## What it is
- The app is one self-contained file: `index.html` (HTML + CSS + vanilla JS, no build step, no dependencies except the Figtree and Titillium Web Google Fonts).
- Open it by double-clicking; it runs in any modern browser, without a server (local mode).

## Features
- **One Year Plan** tab: goals of the selected year (`planYear`, year picker in the toolbar) at three levels (Company → Department → Team), each linked to a parent goal.
  - List view (sortable by title/level/team/linked-to) and Tree view (collapsible hierarchy).
  - Filter by level; goals not linked to a Company goal are grouped separately.
  - Goal modal: title, **Team** (the company, a department or a team — the goal's level is derived from it via `levelOf()`, shown as a pill; it is never stored), "Linked to goal" picker, description, deliverables, change history.
  - The word is **Level** everywhere (column, filter, `LEVELS`, `levelFilter`) — not "Type".
- **Team filter** (top bar, `#tf`, all views): same picker as the Team field plus "All teams"; stored in `teamFilter` (a unit id). A department includes its teams. It filters goals on the One Year Plan (tree view keeps ancestors as greyed context) and rocks on Rocks / Rock Review; new goals and rocks default to the filtered team.
- **Rocks** tab: 90-day rocks per quarter. The quarter list (`quarterList()`) is this year's quarters + Q1 of next year + every quarter that has rocks.
  - Owner avatar, status, milestone progress bar (done / overdue / to do), last update, linked goal (tooltip shows full goal chain).
  - Expand a rock to edit milestones inline (title, done toggle, deadline, per-milestone updates, delete). Inline edits are logged to the rock's history (`milestoneChanges()`, shared with the modal).
  - Quick-update popover on rocks and milestones; rock modal with Updates and History tabs.
- **Rock Review** tab: meeting view. Rows = rocks of the selected quarter/team; columns = ISO weeks (header: "Wk n" + Monday date) spanning the quarter, widened to include every milestone deadline.
  - Past week headers red-soft, current week solid accent (and tinted column), future weeks plain.
  - Each dated milestone is a chip in its deadline week (done / overdue / due ≤7 days / to do); clicking a chip toggles done.
  - Left column per rock: owner, title, team tag (hidden when that team is filtered), update icon (hover = latest update, click = quick-update popover), status button, progress bar.
  - Layout is two tables side by side (`.rr-left` fixed, `.rr-right` inside `.rr-scroll`) so only the weeks scroll; `syncReviewRows()` equalises row heights after each render. The update popover is rendered outside the tables so rows can't cover it.
  - Rock Review and Level 10 are held per team (or meeting). Without one chosen, both show the same team picker (`renderTeamPick`): your teams and meetings grouped per department; with a department selected, only its teams.
  - Level 10, Scorecard and Rock Review have a ✕ at the top right of the view (`closeBoardHTML`, action `closeboard`): it sets the team filter to All teams, so the team picker shows again.
  - Light-grey IDS icon (`idsBtnHTML`): opens a popover (`idsOpen`, `idsPopHTML`, `placeIdsPop`) with a text box prefilled "Rock to Discuss: <rock title>" so you can add your question; Add / Enter puts it at the end of the IDS column of the viewed board (else the rock's own board; hidden when neither is a board you may use), Cancel / Esc closes; no duplicates of an open IDS card.
  - Horizontal scroll is kept across re-renders (`rrScroll`); entering the view or changing quarter jumps to the current week.
- Rock modal: left tabs **Details · Milestones** (`modalState.left`), right tabs **Updates · History** (`modalState.tab`).
  - Milestones tab: round done-checkbox, inline name, compact date label that opens the native picker (`showPicker()` on a hidden date input), delete on hover; Enter jumps to the next milestone / adds one.
  - One "Track in <forum>" checkbox per forum with `includeTracked`.
- **Status** is changed via one shared custom menu (`#stmenu`, `openStatusMenu(btn, current, onPick)`), in lists and in the rock modal — not a native `<select>` (the Windows popup can't be styled).
- All pickers share one component, `initPicker(id, {get, set, groups, display, dotOf, allowNone})` (searchable, grouped, level dots). `initGoalPicker` wraps it for goals; `initUnitPicker` is the **Team** field in both modals (the company, then each department with its teams indented; dot = level). Its value lives in a hidden `#f-unit-id` input that fires `change`.
  - Rock "Contributes to goal" (`rockGoalGroups(unitId, year)`): goals of the rock's quarter's year — own team → own department → Company → own department's other teams → other departments.
  - Goal "Linked to goal" (`initLinkedPicker`): only higher levels of the same year, never self/descendants. Team goal → own department → Company → other departments; Department goal → Company; Company goal → nothing.
  - They only filter once the user types (`typed` flag), not on the pre-filled current value.
- **Level 10** tab (`view="l10"`, `renderL10`): the weekly EOS Level 10 meeting, **per board**. Only teams and meetings have a board (`hasBoard` = `isTeamLevel`).
  - If the team filter isn't a board you may see (`boardOk`), `renderL10Pick` shows one-click buttons for your boards that set `teamFilter`.
  - Fixed agenda card (`AGENDA`, 90 min); "Rock Review" jumps to that tab, "To-Do List" / "IDS" flash their column.
  - Kanban columns `COLS`: IDS · To Do · Done. Inline composer (`l10Add`, Enter adds and stays open). HTML5 drag & drop (`moveCard(id, column, beforeId)` — order = order in `S.cards`), logs "Moved from X to Y".
  - Card modal (`cardModal`/`drawCardModal`): title, column switch, owners (multi, the team's members, empty by default, creator is `createdBy`), description editor, Updates/History.
  - Description is a contenteditable (`initRichText`): text pastes as plain text; pasted/dropped images are downscaled (≤1600px, PNG or JPEG if large) and embedded as data URLs. **Always pass stored HTML through `sanitizeHTML()`** (allows simple tags + `data:image/(png|jpeg|gif|webp)` only). Click an image → `openLightbox`.
- **Scorecard** tab (`view="scorecard"`, `renderScorecard`): the EOS scorecard, **one per board** (same teams/meetings and rights as Level 10; team picker `renderScorecardPick` while none is chosen; the Level 10 agenda item "Scorecard" opens it).
  - Grid: **Measurable · Who · Goal · weeks**, oldest left, **this week on the right** (same order as Rock Review; current week accent, future weeks muted). Built like Rock Review: two tables side by side (`.sc-left` fixed, `.sc-right` inside `.sc-scroll`), so only the weeks scroll and the scrollbar sits under them; `syncRows()` (shared with Rock Review's `syncReviewRows`) equalises row heights. `fitScorecard()` measures after every render (and again once the web font has loaded, and after a name/goal edit) in the real font (`textPx`): Measurable is as wide as its longest name plus tags and icons (`SC_TITLE_MIN`–`SC_TITLE_MAX` = 180–420px; longer: … and full name on hover), Goal as wide as its longest goal, a week as wide as `SC_WEEK_TEXT` = "€10.000.000" needs (≈110px); as many whole weeks as fit (at least 6; 13–14 on Full HD). The add row is white like the others. (`table.sc` overrides the generic `table{min-width:820px}`.) Weeks: at least `SC_HISTORY` = 26 back (more if older values exist, max 104) plus `SC_FUTURE` = 10 ahead (`scWeeks(list)`). Opening the view or changing team starts with `SC_PAST_IN_VIEW` = 4 past weeks, then this week, then the future weeks (`scJump`, `scOpened()`; repeated once the web font has loaded, since that changes the widths); re-renders keep the scroll position.
  - Rows: the team's own measurables, and on a meeting's scorecard also the ones **tracked in it** (`m.trackIn`, `scList()` / `scMatches` → `rights.inForum`, like rocks; they show the team tag, and the "BR" tag on their own team). Tracking is tucked away in the row's ⋯ menu (`scMenu`, `scMenuHTML`: "Show in Business Review" per public meeting with `includeTracked`, plus Delete). Rights: `canEdit.measurables` = `canEditRock`, `rights.canSeeMeasurable` (server filters with it), so meeting members see and fill in tracked rows but can't add rows to the team.
  - IDS icon per row (`idsBtnHTML(m, "measurable")`, same popover as Rock Review; `idsOpen = {kind, id, draft}`), prefilled by `measurableToDiscuss(m)`: "Measurable to Discuss: Win rate (24% in wk 41 · goal >= 30%)".
  - Row order: drag the handle left of the name (`.scgrip`, `moveMeasurable(id, beforeId)` puts its rank between its new neighbours) or Alt+↑/↓.
  - Who = only the avatar (dashed circle when empty), a button: a click opens a popover (`scOwn`, `placeScOwner`, `setScOwner`) with the **same owner field as the rock modal** (`initOwnerField({id:"scown", …})` / `ownerFieldHTML(false, "scown")`: searchable list of the team's members); picking sets the owner (on the empty row it starts a measurable and moves to its name); Esc, Tab away or a click outside closes it. `initPicker` and `initOwnerField` return `open()` for pickers shown in a popover. Goal header has a `?` tooltip (`GOAL_TIP`) explaining what you can enter.
  - Works like Excel: every cell is an `input.scc` (`data-sc` = measurable id or `"new"`, `data-k` = `title` / `goal` / Monday ISO date); the grid spans both tables (`scRowIds()`, `scCells(id)`); → from Goal lands on the first visible week. A click selects the whole cell, typing replaces it; Enter/↓, Shift+Enter/↑, Tab/→, Shift+Tab/← (Who is skipped); F2 or double-click edits inside the text (`scEdit`); Esc undoes; Alt+↑/↓ moves a row (rank swap). Pasting a tab/newline block from Excel fills cells from there on and adds rows (`scPaste`).
  - The last row is **always an empty row**: typing in any of its cells, or picking its Who, creates a measurable (`newMeasurable(title, ownerId)`; a name may be empty, placeholder "Name this measurable").
  - Cells are committed on leave (`scCommit`) and updated **in place** (no `render()`), so focus stays; only adding/moving/deleting rows re-renders. Values aren't logged to history; title, goal and owner changes are.
  - **Numbers are Dutch:** shown with `nl-NL` (40.000 · 1,5); `parseNum` reads 40.000 / 1,5 / 1.234,5 / 40k / 1,5M (lenient: "1.5" = 1,5; 1,234,567 the English way). Goals are free text parsed by `parseGoal`: `20+`, `>= 80%`, `≤ 5`, `< 3`, `min 4`, `max 4`, `€40.000+`, `30-40` (range), plain number = at least, `0` = none. `%`/`€`/`$` in the goal set the number format (`fmtNum`). Green = meets the goal, red = not; an unreadable goal is amber-underlined.
- **Home** (`view="home"`, `renderHome`; the logo + name in the top bar is a button, `#homeBtn`; also where the app opens without a route): a greeting, **your teams and meetings** (units you're a direct member of that have a board you may use) as a list with columns Level 10 / Rocks / Scorecard / Rock Review, each cell a link to that view for the team (`goto`: sets `teamFilter`, the view and for Rocks / Rock Review the current quarter) with its key numbers (open issues/to-dos, rocks off track, measurables off goal last week, milestones overdue / due this week), and on the right **My to-dos** (first 8, "All →" = To-dos tab) and **My rocks** of the current quarter.
- **View as** (admins, Azure and mock only: Organisation → People → "View as"; local mode has the "You" picker): `startViewAs(id)` sets `session.userId` to that person and keeps a snapshot of `S`; the app then shows what they see, within what the server sent you (an admin gets everything except private meetings' content and hidden goals). Read only: `save()` is blocked (toast), refreshing from the server pauses (`isIdle`), and Stop (`stopViewAs`, the amber bar above the view, `viewAsBarHTML`) puts back the snapshot and you.
- **To-dos** tab (`view="todos"`, `renderTodos`, after Rock Review): every Level 10 item (IDS and To Do) that has you as an owner, on all boards you may see, grouped per board (organisation order; IDS before To Do). Click an item → card modal; "Open Level 10 →" (`openboard`) opens its board. "Show done (n)" (`todosDone`). The team filter doesn't apply.
- **Profile** page (`view="profile"`, `renderProfile`, no tab: click your avatar / name in the top bar, `.mebtn` / `openProfile`): your name, initials (≤3, empty = from the name: `personInitials(p)`) and colour (`PROFILE_COLORS`, same as the server's, plus a rainbow swatch with a native colour picker for any other colour). Typing updates the preview in place (`profileInput`, `profileDraft`); Save / Enter (`saveProfile`). On Azure the name comes from your Microsoft account on first sign-in only (built-in sign-in often sends no name: then it's made from the e-mail address), so it's yours to change. The rights block lets everyone change only these fields of their own person record (`PROFILE`, `validProfile`).
- **Forums** (Business Review, the 4-weekly team-leaders meeting) are units with `kind:"forum"`. A forum behaves like a team for rocks and the Level 10 board, but has **no goals**.
  - Rocks shown for a forum (`rockMatches`): its own rocks + rocks whose `trackIn` contains the forum (if `includeTracked`) + rocks with status `escalate` (if `includeEscalated`). They stay owned by their own team; edits change the real rock. Tracked rocks show a tag with the forum's initials ("BR").
  - With a forum selected the One Year Plan shows all goals (`goalFilter()` returns ""); new goals don't default to it; the goal Team picker hides "Meetings" (`initUnitPicker(false)`).
- **Roles and rights** — one block, `createRights({units, people, adminEmails})` between `/* rights:start */` and `/* rights:end */`, is **identical in index.html and api/src/core.js** (tests/api-core.test.html fails if they differ: edit one, copy it to the other). The page rebuilds `rights` in `render()` (`refreshRights`).
  - Roles: **admin** = `person.admin` or in the server's `ADMIN_EMAILS` (`adminEmails`, sent with `/api/data`; defaults gk@letsgrow.com + gabrielvdk@gmail.com) · **member** = `person.unitIds` not empty · **pending** = neither (`roleOf`, `myRole`).
  - **Rights flow down, never up:** membership of a unit gives rights on it and everything below (company → everything; department → itself + its teams; team → only itself; forums hang under the company). Helpers: `canEditUnit`, `canEditGoal`, `canEditRock` (also rocks a meeting you're in shows: full edit, but no moving them away), `canSeeBoard`, `myUnits()` (where you may create), `rights.branch()` (team filter), `rights.writeAllowed(person, collection, before, after)` (every save; creating or moving needs rights on the target unit).
  - Everyone assigned sees all goals. **Rocks: you see exactly the ones you can change** (`rights.canSeeRock` = `canEditRock`: your teams and the teams below your units, plus what your meetings show) — the server's `/api/data` sends only those, and `shownRocks` applies the same rule (then narrows to the chosen team). Goals you can't change open read-only (`modalState.readOnly`, `roField`/`roNote`; `drawRockModalReadOnly` remains as a safety net); list controls are disabled/hidden (`statusButtonHTML(…, canEdit)`, `lastUpdateHTML(…, canPost)`), and `APP_ACTIONS` guard with `viewOnly()`. Level 10: only boards you may see (`boardOk`); the Team field offers only your units.
  - **Private meetings** (`unit.private`, e.g. the DT Team, toggle "Private" on the Organisation tab): rights don't flow into them — only direct members see/change their rocks and board, not directors, not admins (`hasRights`, `canSeeContent`, `writeAllowed` checks rocks/cards before the admin shortcut); their rocks never show in other meetings (`inForum`); only members rename, delete or un-private them; admins may add themselves as a member (break-glass). `rockMatches` uses `rights.inForum`. Rocks of a private meeting can't be tracked elsewhere.
  - **Owners** of rocks (one, shown inside the picker like the Team field) and Level 10 cards (several, as chips) use one field, `initOwnerField({unitId, get, set, multi})` + `ownerFieldHTML(multi)` (`modalState.ownerField`): chips + a picker of the unit's **actual members** (`unitMembers`, direct membership only); non-members stay visible as "(not in this team)". A new rock's owner is you if you're a member, else must be chosen (save checks it when the team has members).
  - **Level 10 shows the members** (`boardPeopleHTML`, below the agenda in `.l10side`), and "Private" for a private meeting. The view fills the screen (`fitL10` sets `--l10top`): the IDS / To Do / Done lists and the members list scroll inside their panel; `render()` keeps the scroll position of every `[data-keepscroll]` element.
  - The server enforces it: pending → no data, no writes; every write → `writeAllowed`; `/api/data` only returns the cards of boards you may see. The remote backend doesn't send changes `writeAllowed` refuses (and then doesn't move the data version either).
  - Pending people see only the waiting page (`waitingHTML`; on Azure `showWaiting()` polls every 30 s). `render()` hides the tabs (`body.gated`).
  - **The organisation manages itself** (no admin needed day to day). Two rules, both in `createRights`: (1) content and membership: you change goals, rocks, cards (`canEditGoal`/`canEditRock`/`canEditCard`) and add/remove people (`canManageMembers` = `hasRights`) in your units and everything below them; (2) structure: you create, rename, reorder, move and delete units *below* your units (`canManageUnit(u)` = rights on the unit above u), never your own. `writeAllowed` checks units (rights on the parent before and after; no new company; no kind change) and people (only `unitIds` may change, and every added/removed unit must be yours; created at sign-in, never by members; `admin` only by admins). Meetings work like teams; directors manage meetings and their rules.
  - Admins can always do everything, even without any unit (so they can always put people back), and are the only ones who grant admin. `ADMIN_EMAILS` is the break-glass entry.
  - **Organisation** menu item (`view="org"`, `renderOrgPage`, everyone assigned) with two tabs (`orgTab`): **Organisation** (`renderOrg`: the org tree; controls only where `canManageUnit` / `canEditUnit`: rename inline, "+ Team" for department members, "+ Department"/"+ Meeting" for directors, drag the grip to reorder or move (`orgDropPlace` / `moveUnit`, checked with `writeAllowed`), delete only when a unit has no teams, members, goals, rocks or cards (`unitUsage`)) and **People** (`renderPeople`: waiting first; "+ Add to…" lists only units you manage, × only on those; Admin tickboxes for admins only, others see an "Admin" pill; removing yourself asks first). Badge with the number waiting on the menu item and the People tab.
  - New goals/rocks default to the filtered team if you may edit it, else your own first unit (`defaultUnitId`); on the first visit the team filter is set to your team/department.
- **Modals** all work the same way: they edit a working copy (`modalState.obj`) of the record (`modalState.orig`); `MODALS[kind].sync()` copies visible fields into it (a no-op for fields not rendered — call it before every redraw); Save writes it back and logs history. Closing (✕, Cancel, Esc, backdrop) with unsaved changes asks "Discard your unsaved changes?" (`requestCloseModal()`, compares against `modalState.snapshot`).
- **Bookmarkable address:** `#<tab>/<team id>` (e.g. `#scorecard/3f2c…`), written on every render (`writeRoute`, `history.replaceState`, keeps `?backend=…`), read at start-up after the prefs (`applyRoute`, wins over them) and on `hashchange`. Ids, not names, so renaming a team keeps links working; a team outside your branch is dropped by `render()`.
- Light/dark theme follows the OS (`prefers-color-scheme`) until the round toggle (fixed bottom right, `#themeBtn`) is clicked; the choice is saved in localStorage key `eos-theme` and applied by a tiny script in `<head>` before first paint.

## Data model (ready for multi-user; see the comment block "data model" in the script)
- All shared data lives in one object `S = {version, people, units, goals, rocks, cards, measurables}` (one per organisation; later: the database).
  - `units = [{id, kind:"company"|"department"|"team"|"forum", name, parentId, rank}]` — a team's `parentId` is its department; forums also have `{includeTracked, includeEscalated, private}`. **Rocks and Level 10 cards live on teams and meetings only** ("team level", `isTeamLevel` / `rights.teamLevel`, enforced for everyone incl. admins); goals on any level. For department- or company-level work, add a management team ("Sales MT").
  - `goals = [{id, unitId, year, title, parentId, visibleTo, description, deliverables, history}]` — level is derived, never stored. `visibleTo` = a private meeting's id: the goal is hidden from everyone else (`rights.canSeeGoal`; the server filters goals; `goal(id)` and `visibleGoals()` only return what you may see). New company goals default to your private meeting (`defaultVisibility`); the goal modal's "Visibility" switch toggles it (a meeting picker appears only if you're in several private meetings); publishing asks first; `levelPillHTML` shows "Company 🔒" in red (`.lvl-hidden`). A public goal links only to public goals.
  - `rocks = [{id, unitId, quarter:"Q4 2026", rank, title, ownerId, status, goalId, trackIn:[forum id], description, deliverables, milestones:[{id, title, done, deadline, updates}], updates, history}]`.
  - `cards = [{id, unitId, column, rank, title, description, owners[], createdBy, createdAt, updates, history}]`.
  - `measurables = [{id, unitId, rank, title, ownerId, goal (text), values:{"YYYY-MM-DD" Monday: number}, trackIn:[forum id], history}]` — the Scorecard; team level only, rights like cards (`canEdit.measurables`, server sends only boards you can see).
  - `people = [{id, name, initials, color, email, unitIds, admin}]` (`initials` optional: set on the Profile page) — on Azure everyone who signs in is added automatically (matched on email) with `unitIds: []` (pending). `unitIds` = membership (teams, departments, meetings or the company).
  - `rank` is the display order (a database keeps no array order): `S.units` / `S.rocks` / `S.cards` are kept sorted by it (`byRank`); new records get `nextRank(list)`; `moveCard` puts a card's rank between its new neighbours.
  - `updates` and `history` entries are `{at, who, text}`, newest first; `at` is an ISO timestamp (older entries may be a plain date, older updates have no `who`). Always add them via `addUpdate(obj, text)` / `logHist(obj, text)`, which fill in author and time.
  - **Everything refers to other records by id, never by name** (rename a team = change one `units` entry). Ids come from `uid()` (`crypto.randomUUID`); sample records keep short ids like `g1`, `r1`, `p1`.
  - Status and column values are **keys** (`STATUSES[].key`: `not_set`, `on_track`, `off_track`, `escalate`, `done`, `cancelled`; `COLS[].key`: `ids`, `todo`, `done`); labels are only for display (`statusOf(key).label`, `colLabel(key)`).
- Lookups: `goal(id)`, `rock(id)`, `card(id)`, `person(id)` / `personName(id)`, `unit(id)` / `unitName(id)`; organisation: `company()`, `departments()`, `teamsOf(deptId)`, `forums()`, `deptOf(id)`, `isDept(id)`, `isForum(id)`, `levelOf(id)`, `goalLevel(g)`, `unitMatches(id, filter)`, `isTeamLevel(id)` / `hasBoard(id)`, `boardOk(id)` (a board you may use).
- **Session:** `session.userId` / `currentUserId()` is the signed-in user, set by the backend on load (Azure: your person record; local: the person picked in the top bar "You", remembered as `prefs.fakeUserId`). Everything that records an author reads `currentUserId()`.
- **Backends** (section "backends" in the script) are the only code that knows where data lives. `backend.load()` fills `S`; `save()` (= `backend.save()`) stores changes — the rest of the app only changes `S` and calls `save()` + `render()`. `pickBackend()` chooses at start-up:
  - **local** (`localBackend`): localStorage key `eos-tracker-data`, used when there is no API (double-click, serve.ps1, GitHub Pages). If saved data can't be read, it shows sample data and refuses to save (`storageProblem`). localStorage holds ~5 MB; pasted images eat it.
  - **api** (`createRemoteBackend("api", httpTransport, config)`): used when `/api/config` answers. `save()` diffs every record against what was last stored (`synced`) and PUTs/DELETEs only changes, with ETags (412 → toast + reload, never overwrite). Retries on connection errors; `beforeunload` warns while changes are pending. `refreshFromServer()` picks up others' changes when idle (tab focus, every 60 s). The server moves pasted images to attachments (`/api/attachments/<sha256>`, allowed by `sanitizeHTML`).
  - **mock** (`?backend=mock`, `&as=email`): the same remote backend, but the transport calls `api/src/core.js` in the browser on a localStorage "database" (`eos-tracker-mock-db`, read fresh per call so tabs act as separate users).
  - `?backend=local` forces local mode. The top bar shows an env tag (Local / Mock API / test), "Saving…" state, and the user (picker in local mode, name + Sign out on Azure). `showGate()` replaces the app for "No access" / server errors.
- **First save of a new database:** the starting records (organisation, or the sample) have fixed ids (`seedId`: `u-direct-sales`, cards `k1…`, measurables `m1…`) and the data version (meta) is stored last; while meta is missing, `fetchAll` starts again from the starting data and keeps what is stored, so a first save that was interrupted (tab closed) is completed on the next visit instead of being taken as the whole data.
- **Migrations:** `migrate()` brings data up to `DATA_VERSION` (now 12) in every backend; on Azure the first visitor's `save()` writes the migrated records back (meta version last; units and people are saved before the rest, so content may refer to a unit created in the same save). When the shape changes, bump `DATA_VERSION` and add a step — never a manual migration. `migrateV7()` converts the old name-based data (key `goals-rocks-v7`); `migrateV8()` adds `rank`; `migrateV9()` adds membership (people join the units of what they own, else the company), unit ranks, and makes the first person admin in data that was never on Azure; `migrateV10()` moves rocks and cards from the company or a department to a new "<name> MT" team (needs an admin to store the new teams on Azure); `migrateV11()` adds `measurables` (sample data, recognised by goal id `g1`, gets the sample scorecards from `seedMeasurables`). Older code refuses to load newer data (rollback safety).
- **Server** (`api/src/core.js`): roles as above (`ADMIN_EMAILS`, pending people get `{waiting:true}` from `/api/data`), allow-list via `ALLOWED_EMAIL_DOMAINS` / `ALLOWED_EMAILS` (empty = nobody, `*` = anyone who can sign in; defaults in infra: `*@hoogendoorn.com,*@letsgrow.com` + `gabrielvdk@gmail.com`), people auto-registered on first `GET /api/data`, records validated (collection whitelist, id format, ≤2 MB). Keep it runnable in both Node and the browser, and add a test to `tests/api-core.test.html` for every change.
- **Personal view settings** are kept apart from shared data: `eos-tracker-prefs` = `{teamFilter, quarter, planYear, fakeUserId}` (`loadPrefs` / `savePrefs`, saved on every render), plus `eos-theme`.
- **Organisation (real):** Hoogendoorn (company) → Product & Technology (Data Science, Research, LG Dev, IIVO Dev, Hardware, Controls), Operations (Engineering, IIVO Helpdesk, LG Service Desk, Customer Success, Contracts, T&C), Sales (Project Sales, Direct Sales), Finance (Legal, Accounting, Business Strategy), HR (no teams yet: add an "HR" team for a board). Forum: Business Review.
- `seed()` contains sample goals/rocks/cards (fictional content, real team names, `DEMO_YEAR` 2026) with **test personas** named after their role — three directors (Director - CEO, Director - CPTO, Director - Sales: Hoogendoorn + DT Team), Head of Sales, Head of Product & Technology, Direct Sales member, Project Sales member, Ops team lead (LG Service Desk + Business Review), Data Science member, Research member, New joiner (waiting), Admin (no team) — plus fictional colleagues who own rocks and to-dos. On top of the real org it adds Sales MT, Product & Technology MT plus the real **DT Team** (a private meeting, `seedOrg`) with only the three directors in it; heads of department are in their MT team and Business Review; every persona's teams have goals, rocks, a filled Level 10 board and a scorecard with 12 weeks of numbers (`seedMeasurables`, relative to today). Pick a persona under "You" (local mode) to test. It is used for a browser with no saved data (clearing site data starts fresh) and for an empty Azure database with `SEED=sample` (Test). With `SEED=org` (Prod) an empty database starts with `seedOrg()` only.
- The initial org structure comes from `seedOrg()`; after that admins maintain it under Organisation.

## Code layout (inside the `<script>`, in this order)
constants · ids & dates · session · data model & sample data · migration · backends (local / api / mock) · ui state · helpers (incl. the rights block and roles) · shared renderers · views (`renderPlan`, `renderRocks`, `renderReview`, `renderL10`, `renderOrg`, `renderPeople`) · `render()` · quick-update popover · status menu · confirm dialog · modals (goal, rock, card) · pickers · rich text · tooltips · theme · events · top bar (`drawTopBar`, `refreshFromServer`) · `init()` (async: pick backend → load → render).

Rendering is "re-render everything": change `S`, call `save()` and `render()`. `VIEWS[view]()` builds `#app`.

Events are delegated: `data-act` inside `#app` → `APP_ACTIONS` (clicks) / `APP_CHANGES` (change events); `data-m` inside `#modal` → `MODAL_ACTIONS`. Add a handler there rather than a new listener.

## Conventions
- **Screen target: Full HD (1920×1080) in a desktop browser.** Use the space (large modals are fine), fit views to the screen height and let long lists scroll inside their panel rather than the page.
- **Look and feel follows [DESIGN.md](DESIGN.md)**, shared with Roadmapper (`gabrielvdk/roadmap-proto`). This app is its source of truth: when you change a token or style recipe, update DESIGN.md here **and** in `../Roadmapper`. Fonts: Figtree for everything (`--font-body`), Titillium Web only for titles (`--font-title`: app name, view `h1`, modal title).
- Colors are CSS variables on `:root`, with dark-mode overrides; use the tokens rather than hard-coded colors.
- Always escape user text with `esc()` when building HTML strings.
- Log meaningful changes to an item's history with `logHist(obj, text)`; post updates with `addUpdate(obj, text)`.
- Refer to records by id; show names via `unitName()` / `personName()`. Replace records in `S` by id (`replaceById`), never by object identity — `S` can be reloaded from the server while a modal is open.
- Test changes in local mode, and with `?backend=mock` when they touch saving, loading or the API.
- **Never use `window.confirm()/alert()/prompt()`** — they are silently blocked in Claude Code's browser pane (and some other embedded browsers). Use `askConfirm(message, okLabel)` (returns a Promise<boolean>) for confirmations.
